# Task And User Authority

Read this reference only when structural adoption, migration, or governance repair must create or change a project's complete Task chain. Routine and explicit Task-file work is governed directly by the local `AGENTS.md` and does not trigger this skill.

The standard path is `docs/03-task.md` for an English-authority project or `docs/03-计划事项.md` for a Chinese-authority project. Keep one authoritative language and use the standalone language-matched Task template.

## Authority And Non-Interference

The user's latest instruction defines the current task, scope, order, and authorization. The Task file is an automatically maintained user-facing display, not Codex Plan mode, a scheduler, execution plan, approval gate, state machine, recovery source, or authority.

Do not read it before ordinary work merely because work is long, related, handed off, or compressed. Read it only when the user explicitly requests Task-file work or the local turn-close rule has already found a preservation candidate and authorizes one narrow maintenance read. Existing items stay inactive. A reminder cannot trigger another read.

## Maintenance And Verification

- Replace obsolete state; keep one concise current statement per item.
- Keep only the next action, direct prerequisite, and minimal background.
- Leave one blank line between distinct items.
- Move logs, hashes, commands, completed decisions, and durable results to their actual owners before removing completed items.
- Remind at most once, only after completed-work writeback exposes a direct listed follow-up.
- Preserve the machine projection owner `task`; it is an interface, not a Skill.

Treat unauthorized start-of-task reading, scope changes caused by Task content, activation of old items, Codex Plan confusion, repeated reminders, mixed history, or language drift as hard failures.
