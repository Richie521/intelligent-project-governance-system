# Writeback And Sync

Use this reference when deciding what should become durable project memory or reusable central method.

## Writeback Decision

Write back governance material only when the result changes future routing, authority, governance verification, safety, recurring diagnosis, durable governance decisions, pattern status, or sync status.

Do not write back:

- raw conversation flow;
- temporary command output;
- unverified guesses;
- private data, credentials, local account material, raw logs, or runtime state;
- adopted-project business context into a central method source.

## Governance Outcomes

- Local governance files: source boundaries, topic routing, governance decisions, verification rules, confirmed wording, or domain governance.
- Central method: only a verified reusable governance pattern or method gap.
- Registry or sync state: only an actual adopted-project status change.
- No governance write: one-off corrections and temporary results stay in their current-task owners.

Within local files, keep these responsibilities distinct:

- unified wording: confirmed project wording and later real-use verification;
- run archive: machine-reproducible inputs, versions, parameters, and outputs;
- project log: concise process and conclusions people still need to read;
- decision record: confirmed stable choices.

Do not let one file silently replace all four responsibilities. Raw conversations, credentials, and unrelated private material belong in none of them.

Public release position is outside this governance writeback workflow.

## Separate Escalation Or Promotion Candidates

- Central method: a governance lesson or central method gap verified as reusable through layered diagnosis or pattern validation.
- Registry or sync status: adopted-project state changed.
- Global rule or tooling: text in one project cannot reliably prevent recurrence.

Handle these only after the relevant diagnosis, pattern, or synchronization decision establishes the broader scope. They are not ordinary project writeback destinations.

## Creating A Durable Destination

Reuse an existing owner when its responsibility fits. If none fits, apply four cases:

1. Authorized execution, clear role and path, no change to authority, privacy, or long-term governance: create one focused topic file and update the topic map in the same turn.
2. Change to topic structure, source authority, privacy, or durable governance: explain the role and wait for confirmation.
3. Discussion-only or read-only work: identify the candidate destination and report deferred writeback.
4. One-off content: keep it in the conversation. Create no long-term topic file.

Update source-of-truth or manifest records only when file role or authority changes. This decision belongs to the active conversation, not a background monitor.

Always close with one writeback result.

## Cross-Project Sync

Central patterns normally create discussion, not automatic edits. Local landing must adapt the pattern to the target project and then feed status back to the central registry when applicable.

An explicit user instruction to repair the issue in the Governance Center can authorize one scoped cross-project sync when the local entry or central method defines that phrase. Inspect every target before editing and preserve its adoption state and business boundary. For each runtime-enabled target, mark the request with `contract_tags: ["central_repair_sync"]`. A target without the runtime must not claim a transaction receipt.
