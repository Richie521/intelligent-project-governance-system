# Project Governance

Apply the Intelligent Project Governance System to a real project from its own local evidence, rules, source boundaries, and verification. This skill owns structural governance only. Public release work is outside this governance skill.

## Scope

Use this skill for:

- new-project governance adoption;
- existing-project governance cleanup;
- migration or long-session handoff design;
- source authority, topic routing, selective context, privacy, and durable governance structure;
- governance-language selection and optional unified wording;
- material governance-event logging and machine-evidence boundaries;
- cross-project pattern validation and synchronization;
- explicitly requested layered diagnosis or governance mechanism repair;
- representative governance verification and live activation.

Do not use this skill for an ordinary correction, current-task scope change, ordinary business implementation, an already-defined governance transaction whose projections, target owners, and authorization are fixed by the current task, roadmap-only release ideas, or public release work. The local `AGENTS.md` handles ordinary corrections and lightweight transaction execution. Public release work stays outside this governance skill.

## Core Workflow

1. State the governance problem type, intended read scope, and default exclusions.
2. Read the target project's local `AGENTS.md` first. Use its valid `zh-CN` or `en` governance-language declaration; when absent, select once from the user's primary language and existing entry language, asking only on conflict.
3. Read enabled unified-wording material only when the local entry declares user approval and its owner.
4. Determine the current task only from the user's latest message. Historical plans and handoff notes are evidence, not task routes or authorization.
5. Use the local topic router only when needed. Classify each candidate as source, generated copy, runtime state, report, private material, cache, historical evidence, or draft.
6. Retrieve the smallest useful evidence set. Treat search, summaries, memory, caches, and tool output as locators; verify material claims against current authority or runtime state.
7. Preserve useful local structures before proposing a governance change. Make the smallest authorized correction that changes future behavior.
8. Keep local business facts in the project. Promote a reusable central pattern only after local validation and an explicit synchronization decision.
9. Record a material governance event once in its local owner. Leave ordinary no-change work and pure conversation unlogged.
10. Verify with representative probes and report one governance writeback result.

Human-readable governance Markdown uses semantic line boundaries rather than fixed-column wrapping. Keep ordinary paragraphs and list continuations on one physical line; preserve code, math, tables, quoted blocks, explicit hard breaks, and blank-line paragraph boundaries.

## Manual Layered Diagnosis

Enter full layered diagnosis only after a dedicated user command such as `启动分层诊断` or `请启动治理门禁：检查……`. Ordinary corrections, dissatisfaction, reminders, file conflicts, plan candidates, and governance discussion do not activate it.

After manual activation, diagnose the current task first, then the project mechanism, then global rules, skills, or tooling only when the defect may recur across unrelated projects. Preserve the runtime gate's read-only and completion-receipt requirements.

The inspection order is an internal investigation sequence, not an outline for layer-by-layer advice. Select exactly one primary root cause and one inspection stop. Mark each layer as `primary`, `contributing`, `ruled_out`, or `not_examined`; do not skip a lower layer, inspect above the stop, or attach a recommendation to a non-responsible layer. Use `contributing` only when evidence states how that layer amplified the primary cause.

Do not stop at assigning responsibility. Explain the causal failure mechanism and the conditions under which the same class of failure would recur. Define a prevention plan with the repair layer, durable change, recurrence barrier, and representative regression probe. Produce one prevention plan anchored to the primary root cause; do not generate one repair suggestion per inspected layer. After repair, run that probe and report its result, evidence, and recurrence-control conclusion. A correct current result without a passing prevention probe is not a completed diagnosis.

## Live Activation And Sync

- Use a fresh conversation attached to the actual target folder for adoption, landing, or activation probes.
- Explicitly choose a suitable model and reasoning effort for the probe.
- Static files and tests do not prove natural long-term operation.
- Central changes create per-project adaptation work; they do not authorize blind batch copying unless the user explicitly authorizes a scoped sync.
- When the user explicitly authorizes a Governance Center cross-project repair, treat that phrase as the scoped sync authorization. Adapt each project separately; runtime-enabled projects must tag the request `central_repair_sync`. Projects without the runtime must not claim a transaction receipt.
- Update the central registry only after each target project's actual result is known.
