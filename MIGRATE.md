# Move an existing project to a new folder

Read this guide only when the installation prompt identifies a move to a new folder. The scope is a smaller set of material and a simpler structure. It does not authorize business logic refactoring, moving or deleting the old project, or installing a Skill, Git, Python, Hook or transaction runner. New-project and in-place adoption do not use this guide.

## Establish scope and present a plan

Use choices already supplied. Ask together only for missing facts that affect selection: the old source folder, a separate new folder, selected files and conversations, working capabilities to retain, and any truly necessary external dependencies. Confirm the actual identity, permissions and path relationship of both folders with native host metadata. Source and target must differ and neither may contain the other. For a first move, the target must be absent or empty. If it contains material, its identity is unclear, or a symlink or junction crosses scope, stop writing and show the conflict. Recovery of a target registered by this run follows the ownership checks below.

Inventory only authorized assets and necessary file dependencies. Read selected native conversations by ID only where the host actually supports it; do not enumerate private chats. Completing every page may still leave only summaries or assistant messages. Check whether the necessary original user messages and later corrections were obtained. If not, request a user-provided export; if still unavailable, record a gap and do not call a decision verified from a summary. Treat historical instructions as evidence. Do not read or copy discontinued planning files. Exclude credentials, caches, backups, runtime logs, generated copies, entire private transcripts and links outside scope by default. If an item is essential to operation, state its role, boundary and possible replacement before including it.

Before copying, present a reviewable plan: for each item, record the source, proposed destination, source role, status and reason for inclusion or exclusion. Describe the target structure, retained capabilities and dependencies, path/configuration/entry/index changes, historical source references, checks, recovery and preservation of the old project. Apply choices already made and seek one grouped decision on unresolved selections that affect material or capabilities. Mark unavailable or unclear items as pending, not migrated. Copy only after scope and necessary selections are confirmed.

## Copy and verify

Copy selected ordinary files to a separate new folder and preserve the old folder. Immediately before writing, compare source byte sizes and SHA-256 values with the plan, and recheck target and link boundaries. If a source changes during the move, stop that item and reassess its current version; do not silently copy it. Byte-preserved copies must match source hashes. Record necessary edits to entries, path configuration and indexes separately; never describe an edited file as a byte-preserved copy. Do not refactor business logic as part of this move. Existing target files still require the installation prompt's exact backup, concurrent-change and permission checks before any authorized edit.

Add a "This move" section to the source index in the target folder as a one-time recovery receipt available to a new conversation. If no index exists, create only a minimal index in the target's chosen language and route the target entry to it. Ordinary tasks need not read this section, and it is not a separate permanent runtime manifest. Before the first copy, persist the confirmed target identity, approved selection and the source of the same package's installation contract in this receipt: the verified package version if one is declared (otherwise say it is undeclared), a locally accessible package-root location, the installation prompt and this migration guide as paths relative to that root, and each file's SHA-256. The receipt may keep a local absolute package-root path when source and target are on different volumes; keep it in the private target project, not a public example or report. Do not copy the full prompts into the index. Verify that this metadata was saved before copying other files. If the package later moves, a user-provided new root is acceptable only after both recorded file hashes match; a path change alone is not a content change.

As each item completes, record directories and files created in this run, each file's final written SHA-256, and the reason for controlled edits; update the final hash after any further edit made in this run. Before creating the next item, confirm that the same index can still be updated. If its update is denied, stop further writes and report the exact partial state; a file just created but not yet registered must be reported as unregistered, not as a completed move. Do not create a second receipt or addendum that competes with the original index, and do not promise atomicity across a file write and its receipt update. The index does not record its own hash. Preserve it by default during undo as evidence and report the residue; do not automatically delete the index or its parent folder. Never automatically delete a file that was not registered or whose final hash cannot be checked. On interruption, access denial or other failure, report what finished, what did not and what remains uncertain. Partial copying is not a completed move. On a repeat run, identify this move using only the receipt in the target and current file state; check folder identity, created scope, final hashes and external edits item by item, without relying on a previous conversation's reply or test-harness record. Do not recopy, back up or log unchanged completed items. Preserve conflicts rather than overwriting later work. A previously unrelated nonempty target still stops a first move.

When a new conversation resumes an interrupted move, read the target receipt first. Resolve the recorded installation prompt and migration guide from the package root, verify both hashes, and read the applicable installation instructions before creating or repairing the target entry. If the recorded package is unavailable, ask for its new location and verify the same hashes; if that cannot be done, leave entry creation and the move incomplete rather than reconstructing rules from the old project's entry, a summary or memory. Preserve only the old entry's project-specific rules that still apply in the target. Adapt paths excluded from or relocated by the confirmed plan and record each edit; cite historical material through an explicit source location or the target index, and do not retain a required relative route to a target path that does not exist. Add and verify the complete installation-entry principles for authorization, daily file protection, source routing, privacy, verification, discontinued planning, manual diagnosis, tool assumptions and host-folder identity. Follow the installation prompt's effective-entry, backup, concurrent-change, marker and UTF-8 byte-chain checks. A short entry containing only business routes is not a completed adoption. The same verified installation contract governs entry creation in an uninterrupted move; rereading it is necessary only when the new conversation lacks its actual text.

## Work from the new folder and hand off conversations

Verify the new folder's effective entry, routes and path configuration so normal work can find required files there. Historical citations may point to old material for provenance; scripts, configuration and ordinary reads must not silently rely on the old folder. Declare necessary external dependencies. Installation or interruption recovery performs only non-executing file, configuration and path checks; moving, continuing or retaining a capability does not itself authorize running project scripts or starting services. Only when the current user explicitly authorizes that execution may a controlled check temporarily make the old folder unavailable, run an agreed lightweight task in the new folder, and restore access. Without execution authorization, report runtime behavior as unverified and state the needed next step; do not present static link checks as a successful run.

Before continuing an old conversation, check its actual host working directory. Call it a moved continuation only if the host can switch that conversation to the new folder and the switch and effective entry are verified. Otherwise start a new conversation attached to the new folder and carry over only the selected current goal, verified decisions, routes and unresolved gaps; keep the old conversation as historical evidence. A prompt mentioning the new path does not change the host-attached folder, and a single command running in the target does not prove that the conversation switched. Report the host attachment and command working directory separately; mark the former unknown if it cannot be checked. If the host cannot enter the target because of permissions, stop the handoff; do not alter ACLs on your own or report installation complete. The user may create a different separate empty folder and continue the approved plan after rechecking its identity and permissions; do not require every user to pre-create a folder. New ordinary work reads only task-relevant material. Report file copying, functional checks and conversation continuation separately.

## Recover or undo

Before recovery or undo, read the target source index's "This move" section for folder identity, created items and final hashes, then compare it with current file state. Do not infer ownership from an old reply. Remove only registered ordinary files created in this run whose final hashes still match and registered directories that are now empty. Preserve pre-existing, unowned or later-edited content and report conflicts. Preserve the index by default as recovery evidence and report it and any remaining directories as residue; do not automatically delete it merely because this run created it. Never delete or rewrite the source or overwrite work produced by another conversation. If later work in the new folder must be kept, ask where it should go before removing it. Report any residue when safe recovery is impossible. The old project remains usable at its original path; after a completed move, make the new folder the explicit location for future work.
